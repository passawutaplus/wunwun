# 01 · เขียนใหม่ หรือปรับจากของเดิม

> **คำตัดสิน: ปรับจากของเดิม แต่รื้อแกนข้างใน** (Option B)
> คงเปลือกแอป, UX, ตัวอ่านวันเวลา, จดด่วน, tray, คีย์ลัด, แคปจอ และหน้าตาเดิมไว้
> แต่เปลี่ยน 3 แกนหลัก: **ที่เก็บข้อมูล** (JSON + HTML → SQLite แบบรายการ), **ตัวแก้ไขโน้ต** (contenteditable ทั้งก้อน → block editor) และ **IPC** (handler กระจัดกระจาย → router ที่ตรวจทุกข้อความ)
> ไม่เปลี่ยน stack: Electron + Vanilla JS ต่อไป

---

## 1. สภาพโค้ดตอนนี้ (v1.1.0)

| เรื่อง | ตอนนี้ | ปัญหาเมื่อจะโตต่อ |
| --- | --- | --- |
| ขนาด | ~4,200 บรรทัด, 30 IPC handler, ไม่มี build step | ยังเล็กพอจะรื้อได้ในไม่กี่สัปดาห์ |
| ที่เก็บข้อมูล | JSON ไฟล์เดียว, โน้ตเก็บเป็น HTML ทั้งก้อน (`contentHtml`), รูปเป็น base64 ในไฟล์ | หา "งานที่ครบกำหนดวันนี้" ต้อง regex HTML ทุกโน้ต, ซิงก์ได้แค่ทั้งโน้ต (แก้คนละบรรทัดบนสองเครื่อง = ทับกัน), ไฟล์โตเร็ว |

| ซิงก์ | stub ที่ไม่ส่งข้อมูลจริง | ต้องออกแบบใหม่ทั้งหมดอยู่แล้ว |
| สิ่งที่ดี | ตัวอ่านวันเวลาไทย + เทสต์ 39 ข้อ, จดด่วน, tray/คีย์ลัด, dock, snip, หน้าตา, การเตือน (ตรรกะ) | ใช้ต่อได้ทันที |

## 2. ทางเลือก

- **A. แพตช์ต่อจากของเดิม** — เพิ่มฟีเจอร์บนโครงเดิม (HTML blob + JSON)
- **B. ปรับจากของเดิม แต่รื้อแกน** — ย้ายโค้ดเข้าโครงสร้างใหม่ เปลี่ยน data layer, editor, IPC; ใช้ส่วนที่ดีต่อ
- **C. เขียนใหม่ด้วย Tauri** (Rust + WebView2) — แอปเล็กลงมาก แต่ logic ฝั่ง main ต้องเขียนเป็น Rust
- **D. เขียนใหม่ด้วย Electron + React/TypeScript** — ขัดข้อจำกัด "Vanilla JS, ห้ามเพิ่ม framework ถ้าไม่จำเป็น"

## 4. ทำไมเลือก B

1. **ซิงก์และ Today view ต้องการข้อมูลทีละรายการ ไม่ใช่ HTML ทั้งก้อน** — ทางเดียวที่จะได้คือเปลี่ยน data model ซึ่ง A ทำไม่ได้โดยไม่กลายเป็น B อยู่ดี
2. **โค้ดยังเล็ก (~4,200 บรรทัด)** — รื้อแกนคุ้มกว่าแบกหนี้เทคนิคไปตลอด
3. **ไม่ต้องเรียนภาษาใหม่** — C ได้ความเบา แต่ต้องเขียน tray, hotkey, scheduler, sync, ไฟล์ ใหม่ใน Rust ทั้งหมด เสี่ยงเกินไปสำหรับทีมคนเดียว
4. **ผู้ใช้เดิมไม่เสียข้อมูล** — B มีขั้น "นำเข้าข้อมูลเดิม" ที่ทดสอบได้ และเก็บไฟล์เดิมไว้ตลอด
5. **ส่วน renderer เป็น ES module ล้วน** — นำไปทำเว็บ/PWA สำหรับมือถือภายหลังได้ (ใช้ block renderer และ when-parser ชุดเดียวกัน)

ความเบาของ Electron ยังเป็นจุดอ่อน → แก้ด้วยการออกแบบ (ดู §6) และกลับมาพิจารณา Tauri ถ้าผู้ใช้บ่นเรื่องขนาดจริง

## 6. ทำให้ Electron เบาขึ้นโดยไม่เปลี่ยน stack

- หน้าต่างจดด่วนสร้างไว้ล่วงหน้าแบบซ่อน (มีแล้ว) — เปิดได้ทันที
- **Dock รวมหน้าต่างเดียว**: โน้ตที่ย่อแล้วจะปิด renderer ของตัวเอง และไปแสดงเป็นแถวใน dock window เดียว (ประหยัด RAM ทีละ renderer)
- ส่ง event เฉพาะรายการที่เปลี่ยน (`items:changed {noteId, ids}`) แทนการส่ง store ทั้งก้อน
- รูปเก็บเป็นไฟล์ + thumbnail ไม่อยู่ใน DB
- เป้าหมาย: เปิดเครื่องถึง tray < 1.5 วินาที, จดด่วนขึ้น < 100 ms, RAM < 300 MB เมื่อเปิดโน้ต 5 ใบ (วัดตาม `10-quality.md`)
